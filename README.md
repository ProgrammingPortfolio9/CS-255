# CS-255: System Analysis and Design

This repository contains my portfolio artifacts from CS-255, including the Business Requirements Document (Project One) and the System Design Document (Project Two).

# Portfolio Reflection

# 1. DriverPass Project Summary
The client was DriverPass, an organization that offers driver education and testing. They wanted a centralized web application to replace their manual processes. The system needed to let students register, study course materials, take practice quizzes, schedule in-person driving tests, and pay online, while giving staff tools to manage bookings and student records.

# 2. What I Did Well
I did a good job breaking down complex requirements into clear, visual diagrams. Mapping out user roles (students, instructors, admins) with use case and data flow diagrams helped clarify how data moves through the system and made it much easier to design the database and core user flows without missing key steps.

# 3. What I Would Revise
If I could redo part of this project, I would spend more time detailing the non-functional requirements in the System Design Document. Specifically, I would define clear performance expectations, such as how the system handles spikes in test-takers at the same time and exact database validation rules for user input.

# 4. Interpreting User Needs
I focused on the client's day-to-day pain points—like scheduling conflicts and manual recordkeeping—and turned them into direct system features. Considering user needs is critical because a system can have great technical architecture, but if it is confusing or doesn't solve the user's actual problems, it won't be used.

# 5. Approach to Designing Software
My approach is to understand the problem before jumping into technical solutions:
- Start with the end user: what problems are they facing, and what tasks must they complete?
- Map things out visually with flowcharts and data diagrams to spot flaws early.
- Keep the design modular so features can be updated or scaled
